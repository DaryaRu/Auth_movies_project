# ТЗ: Профили пользователей

Приоритет: высокий — CRUD/безопасность/доступ, средний — важные пользовательские и админские функции, низкий — второстепенные улучшения.

## 1. CRUD профиля пользователя *(высокий приоритет)*

- Добавить в профиль ФИО. Можно задать сразу при регистрации (необязательное поле) или заполнить/отредактировать позже через профиль.
- Пользователь может получить свои данные профиля.
- Пользователь может отредактировать ФИО. Смену телефона нужно подтверждать отдельно из соображения безопасности.
- Пользователь может удалить/деактивировать профиль. Есть несколько вариантов, как это сделать. Нужно решить, что при этом происходит с его закладками/рейтингами/рецензиями/подписками.

**Задачи:**

### 1.1. CRUD профиля пользователя: чтение и редактирование *(8 баллов, высокий приоритет)*

- Добавить `full_name` в `users` *(1 балл)*: поле необязательное, доступно и в регистрации (`UserRequestScheme`), и в редактировании профиля.
- Добавить эндпоинт для получения персональных данных **`GET /users/me/`** *(1 балла)*: нужен эндпоинт, отдающий текущий `UserResponseScheme` с `full_name`.
- Добавить эндпоинт для обновления ФИО **`PATCH /users/me/full-name/`** *(1 балла)*: по аналогии с имеющимися `/change-email/`, `/change-password/`.
- Смена номера телефона с подтверждением *(5 баллов)*: сейчас `phone` вообще нельзя изменить после регистрации. Так как телефон используется для 2FA (пункт 10) и подтверждения удаления (1.3), смена должна быть защищена похожим образом, но своим сервисом, со своими Redis-ключами и своими настройками TTL/лимитов: `POST /change-phone-request/` (тело — новый номер и текущий пароль, по образцу уже существующего `/change-email/`) проверяет пароль, формат и уникальность номера, отправляет СМС-код на новый номер. Код и новый номер хранятся в Redis-хеше `phone_change:{user_id}` (чтобы нельзя было подтвердить код для другого номера). Отправка ограничена дважды — кулдаун и лимит отправок за фиксированный интервал на сам номер. `POST /confirm-phone/` (тело — только код) проверяет код (с лимитом попыток) и только тогда обновляет `phone`. Пока код не подтвержден, старый номер остается рабочим. После успешной смены делать отзыв всех сессий (как у `/change-password/`) и уведомление на email по паттерну `password_changed`.

### 1.2. Удаление/деактивация профиля пользователем *(3, 5 или 13 баллов, высокий приоритет)*

Реализуется только один из вариантов:

- Вариант 1 — удаление через `is_active=False` *(3 балла)*: закладки/рейтинги/рецензии (user_actions-service) и подписки (auth-service) остаются как есть, только блокируется вход.
- Вариант 2а — полное удаление, синхронный вызов *(5 баллов)*: при удалении аккаунта auth-service дергает новый эндпоинт в user_actions-service, который удаляет закладки/рейтинги/рецензии синхронно, до ответа пользователю. Требует retry, если user_actions-service недоступен.
- Вариант 2б — полное удаление, асинхронная очистка по событию *(13 баллов)*: auth-service публикует Kafka-событие (например, `user_deleted`) после удаления/деактивации пользователя, а user_actions-service подписывается на него отдельным консьюмером и удаляет данные по мере обработки. Ни у auth-service, ни у user_actions-service сейчас нет Kafka-интеграции.

### 1.3. Подтверждение при удалении *(2 балла, высокий приоритет)*

Для любого варианта удаления (1.2). Зависит от того, указан ли телефон в профиле (телефон необязателен):

- Если телефон есть, то через СМС-код: переиспользует отправку/проверку кода из пункта 10.
- Если телефона нет, то подтверждение текущим паролем.

## 2. Просмотр профилей пользователей в админке *(высокий приоритет)*

- Список и поиск профилей (телефон, ФИО) в админ-панели.
- Доступ разрешать только тем администраторам, у кого есть право на просмотр личных данных, не всем админам.

**Задачи:**

### 2.1. Список и поиск профилей: backend *(8 баллов, высокий приоритет)*

- Добавить эндпоинт для списка и поиска пользователей **`GET /admin/users/?search=&page_number=&page_size=`** *(5 баллов)*: параметр `search` ищет по email, телефону и ФИО.
- Добавить эндпоинт для детального просмотра профиля **`GET /admin/users/{user_id}/`** *(2 балла)*: отдает полный набор полей (включая `email_verified`, `timezone`).
- Пагинация в auth-service *(1 балл)*: в movies-service и user_actions-service уже есть `PaginationParams`/`PaginationDep`. Завести то же самое в auth-service.

### 2.2. Просмотр профилей в movies_admin *(5 баллов, высокий приоритет)*

- Добавить Django-view для просмотра профилей *(5 баллов)*.

## 3. Закладки, рейтинг и рецензии в профиле *(средний приоритет)*

- В профиле пользователь видит список фильмов, добавленных в закладки, проставленные им самим рейтинги и рецензии. Функционал реализован в user_actions-service (`GET /bookmarks/my`, `GET /likes/my`, `GET /reviews/my`). Данные нужно собрать в едином эндпоинте `GET /users/me/activity/` в auth-service.

**Задача:**

- Добавить эндпоинт для вывода активности пользователя **`GET /users/me/activity/`** *(5 баллов)*: при недоступности user_actions-service отдавать пустые списки, не роняя страницу профиля.

## 4. Отзывы и рейтинг на странице фильма *(низкий приоритет)*

- На странице каждого фильма отображать пользовательский рейтинг и список рецензий (в дополнение к существующему `imdb_rating`).

**Задачи *(5 или 13 баллов)*:**

Реализуется только один из двух вариантов:

- Вариант 1 — синхронный вызов *(5 баллов)*: movies-service на каждый запрос фильма дергает `GET /likes/movie/{id}/stats` и `GET /reviews/movie/{id}` в user_actions-service, добавляет информацию в ответ. Проще, но добавляет задержку и связанность между сервисами. При недоступности user_actions-service нужно деградировать (отдавать фильм без рейтинга), а не падать.
- Вариант 2 — асинхронное обновление *(13 баллов)*: user_actions-service публикует Kafka-событие при создании/изменении/удалении лайка или рецензии. Консьюмер (новый или существующий для ETL) при получении события заново считает средний рейтинг и количество рецензий по фильму и обновляет Elasticsearch-индекс фильмов. У user_actions-service сейчас нет Kafka-интеграции.

## 5. Смена таймзоны *(средний приоритет)*

- Пользователь может изменить свою таймзону после регистрации (сейчас таймзона задается только один раз при регистрации, эндпоинта для изменения нет). Таймзона нужна для рассылок.

**Задача:**

- Добавить эндпоинт для смены таймзоны **`PATCH /users/me/timezone/`** *(2 балла)*: таймзона используется для запланированных рассылок в notifications-service. Смена должна применяться только к будущим рассылкам.

## 6. Отключение уведомлений *(средний приоритет)*

- Пользователь может сам управлять тем, какие каналы уведомлений ему приходят (email/sms/push) и приходят ли вообще. Добавить CRUD-эндпоинты для отключения уведомлений.

**Задача:**

- Добавить эндпоинты для управления настройками уведомлений **`GET/PATCH /users/me/notification-settings/`** *(3 балла)*: PATCH должен создавать запись, если ее еще нет, а не только обновлять существующую.

## 7. Персонализация рассылок с ФИО *(низкий приоритет)*

- При рассылке (`admin_mailings`) каждому получателю в письмо подставлять его ФИО. Сейчас `payload` рассылки общий для всех получателей (одна и та же структура на весь `admin_mailing_id`), персонализации нет.
- Резолвить email и `full_name` одним batch-запросом на всю аудиторию (аудитория сейчас ничем не ограничена, поэтому батчами).

**Задачи:**

- Bulk-эндпоинт в auth-service **`POST /internal/users/batch/`** *(3 балла)*: принимает список `user_id`, отдает email и `full_name` по каждому.
- Пагинация аудитории *(2 балла)*: аудиторию рассылки сейчас получаем одним неограниченным запросом, что при росте базы тоже не очень хорошо. Получать пользователей стоит постранично, а не одним запросом на всех сразу.
- Батч-резолв в воркере *(5 баллов)*: на каждой странице получателей вызывать `POST /internal/users/batch/` за email+`full_name` и класть в payload каждого сообщения перед публикацией в очередь на отправку. Оба поля берутся из payload, а не из auth-service для каждого сообщения.

## 8. Push-уведомления о новой активности (WebSocket) *(низкий приоритет)*

- Пользователь должен получать push-уведомление, когда кто-то лайкает или дизлайкает его рецензию. Событие сейчас вызывает уведомление только для email. Нужно завести push-вариант шаблона под событие и обеспечить доставку в оба канала.

**Задачи *(5 баллов)*:**

- Push-вариант шаблона `review_liked`/`review_disliked` *(1 балл)*: нужно завести парный push-шаблон под тот же код события.
- Доставка в push *(3 балла)*: сама push-доставка (Redis → ws-gateway) уже работает для других целей, нужно подключить к ней эти шаблоны и решить, уходит ли уведомление в оба канала сразу или только в предпочитаемый.

## 9. История просмотров / «продолжить просмотр» *(низкий приоритет)*

- Получить список недавно просмотренных фильмов и позиция, с которой можно продолжить просмотр.
Analytics-service пишет события `film_progress`/`video_completed`/`film_view` в ClickHouse, использовать эти данные.
- Эндпоинт вызывается напрямую из analytics-service, без проксирования через movies-service.

**Задачи *(8 или 13 баллов)*:**

Реализуется только один из трех вариантов:

- Вариант 1 — эндпоинт поверх текущей схемы *(8 баллов)*: read-запрос к ClickHouse с `JSONExtract`: последнее событие `film_progress` на каждый `film_id` (позиция для «продолжить просмотр») и список недавно просмотренных фильмов по `film_view`/`video_completed`. Поля событий сейчас хранятся не отдельными колонками, а в одной колонке `payload` как JSON-строка, читать их придется через `JSONExtract`.
- Вариант 2 — типизированные колонки в таблице событий *(13 баллов)*: добавить в таблицу событий отдельные колонки под нужные поля (например, `viewed_frame`, `movie_duration`), ETL пишет их отдельно от `payload` при `event_type='film_progress'`. Требует миграции таблицы и правки ETL.
- Вариант 3 — отдельная таблица текущего прогресса *(13 баллов)*: завести таблицу вида `film_watch_progress`, которую ETL обновляет отдельно.

## 10. Двухфакторная аутентификация по телефону *(высокий приоритет)*

- Использовать `phone` в профиле для двухфакторной авторизации при входе: если у пользователя указан телефон, после проверки пароля вход не завершается сразу — сначала нужно подтвердить код, отправленный по СМС.

**Задачи:**

- Интеграция с СМС-провайдером *(3 балла)*: при недоступности/ошибке провайдера выполнять retry (1-2 попытки с backoff), при неудаче выдавать понятную ошибку.
- Генерация и хранение кода в Redis *(3 балла)*: 6-значный код, ключ `2fa_code:{user_id}`, TTL через новую константу по аналогии с `OAUTH_STATE_EXPIRE_SECONDS`. Код одноразовый, удаляется из Redis сразу при успешной проверке (как уже сделано для OAuth state).
- Новый шаг в форме логина *(5 баллов)*: при наличии `phone` у пользователя `/login/` после проверки пароля не выдает токены сразу, а отправляет код. Новый эндпоинт **`POST /login/verify-phone/`** (email + код) проверяет код и только при совпадении выдает токены тем же путем, что и обычный логин. Пользователи без телефона логинятся как раньше, без изменений.
- Rate limiting *(2 балла)*: отправка кода ограничена по номеру телефона, проверка кода ограничена по аккаунту.

- Выбор отображения автора: рецензия на странице фильма показывает реальное ФИО автора, никнейм или анонимна.

**Задача:**

- **Поле приватности рецензии + логика отображения автора** *(3 балла)*: нужно поле и логика на стороне отдачи рецензий — показывать реальное ФИО, автоматический никнейм или «Аноним» в зависимости от выбора автора.

## 12. Топ рецензентов / полезность рецензии *(низкий приоритет)*

- Звание «топ-рецензент» в профиле — на основе уже существующих лайков рецензий (`review_likes`). Сортировка «сначала полезные» на странице фильма уже реализована (`GET /reviews/movie/{id}?sort=likes`).

**Задача:**

- Звание «топ-рецензент» *(3 балла)*: присвоение статуса на основе суммарных лайков пользователя по всем его рецензиям.

## 13. Переделка ролей и прав *(высокий приоритет)*

- Таблицы `permissions`/`roles`/`role_permissions`/`user_roles` в auth-service уже есть, JWT содержит `is_superuser` и `permissions`, но нигде в проекте `permissions` реально не проверяются. Проверка доступа только через `is_superuser`. Нужно сделать аналог `StaffUserDep`, но по конкретному коду права, а не по факту суперпользователя.

**Задача:**

- Переиспользуемая проверка permission-кода *(3 балла)*: по образцу `StaffUserDep`, но параметризованная по конкретному коду права.

## 14. Подписки в профиле *(средний приоритет)*

- В профиле показывать текущую подписку и историю подписок (подключить к профилю эндпоинты `GET /users/me/subscription/` и `GET /users/me/subscription/history/`).
- Добавить самостоятельное оформление/апгрейд подписки самим пользователем. Назначить/отменить подписку сейчас может только администратор.
- Реализовать заглушку вместо реального провайдера оплаты (по тому же принципу, что Mailpit вместо настоящего SMTP): пользователь инициирует переход к оплате, в ответе заглушка «URL оплаты» вместо редиректа на настоящего провайдера. Отдельный эндпоинт-заглушка имитирует вебхук подтверждения оплаты и реально активирует подписку. Флоу получается такой же, как у настоящей интеграции, и заглушку можно будет позже заменить реальным провайдером, не меняя форму.

**Задачи *(13 баллов)*:**

- Подключить существующие эндпоинты подписки к профилю *(2 балл)*: показывать в профиле `GET /users/me/subscription/` и `GET /users/me/subscription/history/`.
- Добавить эндпоинт для самостоятельного оформления подписки **`POST /users/me/subscription/`** *(3 балла)*: сейчас назначить подписку может только администратор (`POST /users/{user_id}/subscription/`, `StaffUserDep`). Требует подтвержденного email, при `email_verified=False` эндпоинт отдает ошибку вместо оформления.
- Добавить эндпоинт-заглушку для перехода к оплате **`POST /users/me/subscription/checkout/`** *(8 баллов)*: инициирует переход к оплате и возвращает заглушку «URL оплаты» вместо редиректа на настоящего провайдера. Отдельный эндпоинт-заглушка имитирует вебхук подтверждения оплаты и реально активирует подписку.
