# Профили пользователей: архитектура

## Принятые решения

- Профиль — не отдельный сервис, а расширение auth-service.
- `GET /users/me/activity/` агрегирует данные (закладки/рейтинги/рецензии из user_actions-service).

**Контроль доступа**

- Permission-код вместо `is_superuser`. RBAC (`permissions`/`roles`/`role_permissions`/`user_roles`) реализован в auth-service, но нигде не используется. Доступ сейчас проверяется только по `is_superuser`. Будем использовать реальную проверку по коду права для доступа к профилям.

**Внешние интеграции**

- В подписках только заглушка оплаты, без реального провайдера. По аналогии с уже принятым в проекте решением про Mailpit вместо настоящего SMTP. Флоу (checkout → редирект → подтверждение → активация) совпадает с настоящей интеграцией, так что замена в будущем не потребует менять контракт.

## Зависимости между пунктами

- **1.1 (смена телефона) зависит от 10** Подтверждение смены номера СМС-кодом переиспользует код из двухфакторной аутентификации.
- **1.3 зависит от 10** Подтверждение удаления СМС-кодом переиспользует код из двухфакторной аутентификации.
- **2.1/2.2 зависят от 13** Ограничение доступа к просмотру профилей только тем, у кого есть право требует реальной проверки permission-кода, без пункта 13 ограничивать доступ нечем.
- **8 зависит от 6** Выбор канала push/email для уведомлений о лайке рецензии зависит от пользовательских настроек (`push_enabled`/`email_enabled`), которые заводит пункт 6.
- **4 зависит от 11** Если рецензия анонимна (пункт 11), это должно учитываться в отображении рецензий на странице фильма (пункт 4). Нужно синхронизировать логику приватности и логику вывода.
- **14 зависит от подтверждения email** Самостоятельное оформление подписки требует подтвержденного email — сейчас это поле нигде не проверяется.
- **Пункт 9 не создает зависимости movies-service → analytics-service** — история просмотров читается внешним клиентом API из analytics-service напрямую, movies-service в этом вызове не участвует.

## Затронутые сервисы по каждому пункту ТЗ

### 1. CRUD профиля пользователя

**Затронутые сервисы:** auth-service; user_actions-service — только при полном удалении профиля.

- auth-service: нужна миграция с добавлением поля `full_name` в `users`. Поле необязательное, доступно и в `UserRequestScheme` (регистрация), и в редактировании профиля, общий валидатор на обе схемы. Добавить новые эндпоинты `GET /users/me/` (получение своих данных) и `PATCH /users/me/full-name/` (обновление только ФИО).
- Смена телефона — отдельный защищенный процесс по той же схеме `change-request`/`confirm`, что и у пункта 10, но свой сервис `PhoneChangeService`, со своими настройками: `POST /change-phone-request/` (пароль + формат и уникальность номера) кладет код в Redis-хеш `phone_change:{user_id}` вместе с новым номером, отправка ограничена кулдауном и часовым лимитом на сам номер. `POST /confirm-phone/` проверяет код (с лимитом попыток) и только тогда обновляет `phone`, отзывает все сессии (как `/change-password/`) и уведомляет на email о смене (по аналогии с `password_changed`).
- Реализовать логику удаления/деактивации профиля (один из вариантов ТЗ). Удаление в любом варианте требует подтверждения: СМС-кодом, если у пользователя есть телефон, если нет, то текущим паролем.
- user_actions-service: при полном удалении аккаунта — вариант 2а принимает синхронный internal-вызов на удаление данных пользователя, вариант 2б требует добавить консьюмер, который слушает событие удаления профиля и удаляет закладки/рейтинги/рецензии. При варианте 1 (`is_active=False`) этот сервис не трогаем вообще. Вариант 2б потребует Kafka-интеграции сразу в обоих сервисах (в auth-service и user_actions-service).

### 2. Просмотр профилей пользователей в админке

**Затронутые сервисы:** auth-service, movies_admin.

- auth-service: добавить пагинацию (`PaginationParams`/`PaginationDep`). Добавить новые эндпоинты `GET /admin/users/?search=&page_number=&page_size=` (список с поиском по email/телефону/ФИО) и `GET /admin/users/{user_id}/` (детальный просмотр профиля). Доступ к обоим эндпоинтам ограничить проверкой permission-кода.
- movies_admin: добавить Django-view. Скрыть пункт меню для администраторов без нужного permission-кода в JWT. Пока доступ в movies_admin проверяется только по `is_superuser`.

### 3. Закладки, рейтинг и рецензии в профиле

**Затронутые сервисы:** auth-service.

- auth-service: добавить новый эндпоинт `GET /users/me/activity/`, который параллельно вызывает уже существующие `GET /bookmarks/my`, `GET /likes/my`, `GET /reviews/my` в user_actions-service. Реализовать частичную деградацию (пустые списки вместо падения) при недоступности user_actions-service.
- user_actions-service: изменений не требует. Используются готовые эндпоинты.

### 4. Отзывы и рейтинг на странице фильма

**Затронутые сервисы:** movies-service всегда; user_actions-service, Kafka и Elasticsearch — только при варианте 2.

- Вариант 1 (синхронный вызов): movies-service — добавить вызов `GET /likes/movie/{id}/stats` и `GET /reviews/movie/{id}` в user_actions-service на каждый запрос детали фильма, включить результат в ответ. Изменения только в movies-service. Сейчас у него нет HTTP-вызовов в user_actions-service.
- Вариант 2 (асинхронное обновление): user_actions-service — добавить публикацию Kafka-события при изменении лайка/рецензии. Добавить новый или расширить существующий консьюмер — пересчитывать средний пользовательский рейтинг фильма и количество рецензий (или лайков/дизлайков) на этот фильм и писать в Elasticsearch-индекс фильмов (тот же, что уже использует movies-service для поиска). Читать эти значения прямо из индекса, без вызовов в user_actions-service на чтении.

### 5. Смена таймзоны

**Затронутые сервисы:** auth-service.

- auth-service: добавить новый эндпоинт `PATCH /users/me/timezone/`.
- notifications-service: не меняется, читает актуальную таймзону через существующий эндпоинт `search_user_timezones`.

### 6. Отключение уведомлений

**Затронутые сервисы:** notifications-service.

- notifications-service: добавить новые эндпоинты `GET/PATCH /users/me/notification-settings/` поверх уже существующей таблицы `user_notification_settings`, которую воркер читает перед отправкой.

### 7. Персонализация рассылок с ФИО

**Затронутые сервисы:** notifications-service (worker), auth-service.

- auth-service: новый internal-эндпоинт `POST /internal/users/batch/` — email и `full_name` по списку `user_id` одним запросом.
- notifications-worker: в `_handle_admin_mailing`, сразу после резолва аудитории, батчами вызывать `POST /internal/users/batch/` и класть email+`full_name` в payload каждого сообщения. Убрать из `_render_and_send` поштучный вызов `get_email()`.

### 8. Push-уведомления о новой активности

**Затронутые сервисы:** notifications-service (core + worker), ws-gateway.

- notifications-service: добавить push-шаблоны для кодов `review_liked`/`review_disliked` (сейчас есть только `channel=email`). Реализовать логику выбора канала(ов) доставки на основе `push_enabled`/`email_enabled`.
- ws-gateway: канал push-доставки уже существует и используется для других уведомлений, добавляется только новый трафик через него.
- user_actions-service: не меняется, событие и вызов `notify_user()` есть.

### 9. История просмотров / «продолжить просмотр»

**Затронутые сервисы:** analytics-service. movies-service не затрагивает.

- analytics-service: добавить новый эндпоинт поверх ClickHouse (`film_progress`/`video_completed`/`film_view` пишутся, но не читаются обратно; сейчас в analytics-service нет read-пути, только `POST /analytics/events/`). Выбрать один из трех вариантов хранения/чтения — от `JSONExtract` поверх текущей схемы до отдельной таблицы текущего прогресса с доработкой ETL.

### 10. Двухфакторная аутентификация по телефону

**Затронутые сервисы:** auth-service, внешний СМС-провайдер.

- auth-service: подключить внешнего СМС-провайдера с fail-closed retry (NFR5). Код — 6 знаков, Redis-ключ `2fa_code:{user_id}`, TTL — новая константа по образцу `OAUTH_STATE_EXPIRE_SECONDS`, одноразовый (удаляется при успешной проверке, тем же паттерном, что уже сделано для OAuth state). `/login/` при наличии `phone` не выдает токены сразу, а отправляет код. Новый `POST /login/verify-phone/` завершает вход после проверки кода.

### 11. Приватность отзывов

**Затронутые сервисы:** user_actions-service, movies-service.

- user_actions-service: добавить новое поле в `reviews` (например, `is_public`/`display_name_mode`) и логику на отдаче рецензий с учетом этого поля.
- movies-service: при отображении рецензий на странице фильма учитывать это поле (реальное ФИО/никнейм/«Аноним»).

### 12. Топ рецензентов / полезность рецензии

**Затронутые сервисы:** user_actions-service.

- user_actions-service: реализовать расчет и отдачу звания «топ-рецензент». Сортировка `GET /reviews/movie/{id}` по лайкам из `review_likes` реализована, доработки не требует.

### 13. Переделка ролей и прав

**Затронутые сервисы:** auth-service.

- auth-service: добавить зависимость для проверки конкретного permission-кода (по образцу `StaffUserDep`, но параметризованную).

### 14. Подписки в профиле

**Затронутые сервисы:** auth-service.

- auth-service: показать существующие `GET /users/me/subscription/`/`GET /users/me/subscription/history/` в профиле. Добавить новый эндпоинт `POST /users/me/subscription/`. Добавить заглушку оплаты `POST /users/me/subscription/checkout/` и отдельный эндпоинт-заглушку вебхука подтверждения. Оба self-service эндпоинта требуют проверки `email_verified` перед оформлением (сейчас это поле нигде не проверяется, даже при логине). Другие сервисы не затрагивает.

## Ограничения текущего решения

- **Таблица `user_notification_settings` сейчас на 3 канала** (email/sms/push) — учитывать при проектировании, что добавление нового канала потребует миграции.
- **Двухфакторная аутентификация** — способов подтверждения может быть несколько (СМС в первую очередь), не завязывать проверку на конкретный канал.
- **2FA не проверяется при входе через OAuth** — `authenticate_oauth_user()` создает сессию напрямую, минуя проверку кода из СМС, даже если у пользователя указан телефон (Yandex OAuth умеет сам возвращать `phone` от провайдера). Решить оставить как есть (провайдер уже аутентифицировал пользователя на своей стороне) или требовать код независимо от способа входа, раз телефон защищает не сам логин, а последующие чувствительные действия?
