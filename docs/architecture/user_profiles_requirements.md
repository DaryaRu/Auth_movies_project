# Профили пользователей

## Функциональные требования

- FR1. Пользователь может получить свои данные профиля: email, ФИО, телефон, таймзона, статус верификации email.
- FR2. Пользователь может отредактировать ФИО и телефон.
- FR3. Пользователь может удалить или деактивировать свой профиль.
- FR4. Администратор с правом доступа к личным данным может искать и просматривать профили пользователей по email/телефону/ФИО.
- FR5. Пользователь видит в профиле список фильмов, добавленных в закладки.
- FR6. Пользователь видит в профиле выставленные им рейтинги фильмов.
- FR7. Пользователь видит в профиле свои рецензии.
- FR8. На странице фильма отображается пользовательский рейтинг и список рецензий (в дополнение к `imdb_rating`).
- FR9. Пользователь может изменить свою таймзону после регистрации.
- FR10. Пользователь может включать/отключать отдельные каналы уведомлений (email/sms/push) или все уведомления целиком.
- FR11. Рассылки персонализируются: в письмо подставляется ФИО получателя.
- FR12. Пользователь получает уведомление, когда кто-то лайкает или дизлайкает его рецензию, в том числе push-каналом.
- FR13. Пользователь может посмотреть список недавно просмотренных фильмов и продолжить просмотр с сохраненной позиции.
- FR14. При входе с указанным телефоном пользователь проходит дополнительный шаг двухфакторной аутентификации.
- FR15. Автор рецензии может выбрать, как отображается его авторство: реальное ФИО, никнейм или анонимно.
- FR16. Пользователям с высоким количеством лайков присваивается звание «топ-рецензент».
- FR17. Доступ к чувствительным данным и операциям проверяется по конкретному permission-коду, а не только по признаку суперпользователя.
- FR18. Пользователь видит в профиле текущую подписку и историю подписок.
- FR19. Пользователь может самостоятельно оформить или проапгрейдить подписку без участия администратора.
- FR20. Оформление подписки проходит через заглушку оплаты: инициация возвращает фиктивный «URL оплаты», отдельный вызов имитирует подтверждение оплаты и активирует подписку.
- FR21. Самостоятельное оформление подписки доступно только с подтвержденным email — сейчас подтверждение email нигде не проверяется.
- FR22. Удаление аккаунта (любой вариант) требует подтверждения: СМС-кодом на телефон, если телефон указан в профиле, если нет, то текущим паролем.

## Нефункциональные требования

### Безопасность

- NFR1. Доступ к персональным данным в админке ограничен ролью/правом, а не общим статусом администратора. Не все админы должны видеть телефон и ФИО пользователей.
- NFR2. Код подтверждения для двухфакторной аутентификации хранится временно (с TTL).
- NFR3. Чувствительные операции (например, просмотр профиля пользователя администратором и удаление аккаунта) должны логироваться (кто, когда, какое действие).

### Отказоустойчивость

- NFR4. Эндпоинт с активностью пользователя (`GET /users/me/activity/`, отдает закладки, рейтинги/лайки и рецензии) не должен падать целиком, если недоступен user_actions-service, возвращать пустой список для недоступного блока.
- NFR5. Если СМС-провайдер недоступен или вернул ошибку при отправке кода 2FA — auth-service делает короткий автоматический retry (например, 1–2 попытки с backoff), прежде чем показать ошибку. Если и это не помогло, пользователь видит понятную ошибку с возможностью повторить попытку в рамках лимитов NFR13/14.
- NFR6. Недоступность analytics-service не должна ронять страницу профиля. Эндпоинт истории просмотров должен возвращать пустой список или явную ошибку своего блока, не затрагивая остальные блоки страницы.
- NFR7. Недоступность Redis/ws-gateway не должна ронять доставку уведомлений целиком. Сбой push-канала должен уходить в retry/DLQ по тому же паттерну, что уже используется в notifications-worker для остальных каналов (`notification.dlq`), не блокируя доставку в другие каналы.
- NFR8. Если auth-service недоступен в момент персонализации рассылки (получение `full_name`), воркер должен отправить письмо без персонализации, а не терять получателя целиком или ронять всю рассылку.
- NFR9. Недоступность user_actions-service не должна ронять страницу фильма (movies-service, пункт 4 вариант 1). При ошибке/таймауте запроса к `GET /likes/movie/{id}/stats` или `GET /reviews/movie/{id}` — отдавать фильм без пользовательского рейтинга/рецензий, а не падать целиком.

### Производительность

- NFR10. 95-й перцентиль времени ответа `GET /users/me/`, `PATCH /users/me/full-name/` и `GET /admin/users/?search=` должен быть не более 300 мс (для последнего — плановая оценка, после реализации проверить нагрузочным тестом или по трейсам в Jaeger).

### Масштабируемость

- NFR11. auth-service остается stateless и горизонтально масштабируемым после добавления новых эндпоинтов. Состояние не хранится в памяти процесса, только в Postgres/Redis.

### Расширяемость

- NFR12. Заглушка оплаты подписки повторяет форму запросов настоящей интеграции, чтобы ее можно было заменить реальным провайдером без изменения контракта API.

### Rate limiting

- NFR13. Отправка СМС-кода для двухфакторной аутентификации должна быть ограничена по частоте на номер телефона (например, не более N попыток в час).
- NFR14. Проверка кода 2FA должна быть ограничена по частоте на аккаунт/номер телефона отдельно от лимита на отправку СМС (NFR13). Общий лимитер auth-service работает по IP+User-Agent, а не по аккаунту, поэтому один атакующий с разных IP может подбирать короткий код, оставаясь в пределах лимита с каждого отдельного адреса.
- NFR15. На новые эндпоинты профиля нужно явно навесить существующий декоратор `@limiter.limit(...)` (как у `/change-email/` и `/change-password/`).

### Консистентность и целостность данных

- NFR16. Если для рейтинга/рецензий на странице фильма выбрано асинхронное обновление среднего пользовательского рейтинга фильма и количества рецензий (или лайков/дизлайков) на этот фильм (Kafka + Elasticsearch), допустима задержка обновления данных не более 10 секунд при нормальной нагрузке (плановая оценка, после реализации проверить по трейсам).
- NFR17. При полном удалении аккаунта данные пользователя в user_actions-service (закладки/рейтинги/рецензии) должны быть удалены каскадно, а не остаться храниться без владельца.

### Удобство использования

- NFR18. Поиск профилей в админке регистронезависим и работает по совпадению с начала строки (email/телефон/ФИО).
