# Сервис нотификаций

Архитектура, модели данных, сценарии уведомлений.

## Компоненты

- **База** — хранит уведомления и триггеры уведомлений автоматической генерации:
  - `notification_triggers` — триггеры уведомлений (что и когда проверять при изменении контента);
  - `notifications` — хранит уведомления, которые предстоит отправить, и те, что уже отправлены, привязанные к конкретному получателю;
  - `templates` — шаблоны сообщений;
  - `admin_mailings` — ручные рассылки, создаваемые через админку;
  - `user_notification_settings` — настройки пользователя (какие каналы уведомлений разрешены).

- **API** — единая точка приема для всех источников событий (другие сервисы, шедулер, админка). Валидирует, публикует в Kafka. Часть эндпоинтов (создание рассылки, шаблон по code, upsert триггера) защищена межсервисным секретом `X-Internal-Secret`.

- **Воркер** — читает топики Kafka. Для полностью собранных сообщений (`notification-ready`/`notification-ready-bulk`) рендерит и отправляет. Для триггеров и рассылок (`notification-pending`) резолвит аудиторию и делает fan-out — по одному сообщению на получателя в `notification-ready-bulk`, а не отправляет напрямую. Сбой доставки конкретному получателю не блокирует остальных, уходит в DLQ (`notification.dlq`).

- **Генератор автоматических уведомлений** — шедулер (`notifications/scheduler/`), который работает с `notification_triggers` и `admin_mailings`: читает `notification_triggers` (ищет триггеры уведомлений, где подошло время проверки, по `check_interval`/`last_checked_at`) и пишет туда `last_checked_at` после проверки.
С заданной периодичностью сверяет, какие триггеры уведомлений пора проверить, и для каждого сравнивает `last_update`/`last_notification_sent` — реально ли нужно уведомление. Если триггер уведомления сработал, шедулер выступает Kafka-продюсером, т.е. пишет сообщение в топик `notification-pending`. Тем же проходом проверяет `admin_mailings` со `status=scheduled`, у которых наступил `scheduled_at`.

- **Админка** (Django admin) — админы создают ручные рассылки: выбирают шаблон и сегмент аудитории, вызывают API нотификаций. Шаблонами тоже управляет через API сервиса нотификаций (просмотр/создание/редактирование).

- **WebSocket-шлюз** — `ws-gateway`, отдельный сервис для push-канала. Держит WebSocket-соединения с клиентами (аутентификация тем же JWT, что и остальные сервисы), подписан на Redis Pub/Sub. С Kafka не взаимодействует — только с воркером через Redis.

## Kafka: топики

Все три топика читает один и тот же воркер.

- **`notification-ready`** — полностью собранные сообщения, готовые к рендеру и отправке (`user_id`, `template_id`, `payload`, `channel`, `deduplication_key`).
- **`notification-pending`** — неполные сообщения (Kafka-триггеры) на группу пользователей, без резолва аудитории. Форма зависит от источника:
  - от `notification_triggers`: `content_id`, `notification_type`, `template_id`, `payload`;
  - от `admin_mailings`: `admin_mailing_id`, `template_id`, `audience_filter`, `payload` — без `notification_type`, вместо него `audience_filter`.
- **`notification-ready-bulk`** — результат fan-out рассылки из `admin_mailings`: воркер резолвит аудиторию из `notification-pending` и публикует по одному сообщению на получателя (`deduplication_key = f"{admin_mailing_id}:{user_id}"`) в этот отдельный топик, а не в `notification-ready` — иначе большая рассылка задержала бы в очереди персональные уведомления, идущие следом. Читает тот же обработчик, что и `notification-ready`.

Часть событий приходит в API уже полностью собранной и сразу идет в `notification-ready` (данные собраны до воркера), часть приходит как триггер в `notification-pending` — воркер сам резолвит аудиторию и достраивает недостающие данные, публикуя результат fan-out в `notification-ready-bulk` (по одному сообщению на получателя).

## Данные

### `notification_triggers` — триггеры уведомлений
Любое событие, о котором нужно уведомить пользователя/пользователей. Например: "у сериала, который пользователь добавил в закладки, вышла новая серия" — источник события `movies_admin`, `content_id = tv_show_id`, `notification_type = "new_episode"`.

API, получив от сервиса-источника (например, `movies_admin`) событие "контент изменился" `{content_id, notification_type, template_id, payload}`, делает upsert — если строки с такой парой `(content_id, notification_type)` еще нет, создает ее (`last_update = now()`, `last_notification_sent = null`); если есть — обновляет `template_id`/`payload`/`last_update`. `template_id` передается источником события явно, а не выводится из `notification_type` — сервис-источник должен его знать. Первое событие по новому контенту само заводит для него триггер уведомления.

Данные не сравниваются напрямую (не нужно ходить в БД фильмов, чтобы проверить, изменилось ли что-то), вместо этого есть два независимых таймстемпа, которые можно сравнивать между собой:
- `last_update` обновляется сразу, как только приходит событие об изменении контента, без участия шедулера.
- `last_notification_sent` обновляется только воркером, после того как уведомление реально ушло.

Если `last_update` новее `last_notification_sent` — значит, с последней отправки что-то изменилось, и уведомление нужно.

| Поле | Тип | Назначение |
|------|-----|------------|
| `trigger_id` | UUID, PK | идентификатор триггера уведомления |
| `notification_type` | varchar | `new_episode`, `new_movie` и т.п. — определяет логику подбора аудитории при резолве воркером |
| `content_id` | UUID | ключ к данным, на изменение которых реагирует уведомление (например, ID фильма) |
| `template_id` | UUID (FK) | шаблон для рендера, передается источником события явно |
| `payload` | jsonb | данные для рендера на момент последнего изменения; перезаписывается на каждом upsert — важно только последнее состояние |
| `last_update` | timestamp | когда контент реально изменился — пишется сразу при получении события об изменении |
| `last_notification_sent` | timestamp, nullable | когда по этому `content_id`/`type` последний раз реально отправляли |
| `check_interval` | interval | как часто шедулер должен проверять этот триггер уведомления |
| `last_checked_at` | timestamp, nullable | когда шедулер последний раз проверял триггер уведомления |
| `is_active` | bool | можно выключить триггер уведомления, не удаляя запись |
| `created_at` / `updated_at` | timestamp | даты создания и изменения |

Уникальный индекс: `(content_id, notification_type)`.

Логика шедулера при каждом запуске (с заданной периодичностью):
1. Выбрать активные триггеры уведомлений, где `now() >= last_checked_at + check_interval`.
2. Для каждого сравнить `last_update` с `last_notification_sent`: если `last_update` новее — триггер уведомления должен сработать, публикуется Kafka-триггер.
3. Обновить `last_checked_at = now()` для всех проверенных триггеров уведомлений; `last_notification_sent` обновляет уже воркер после реальной отправки.

Рассылается тем, у кого этот `content_id` в закладках (таблица `bookmarks` в `user_actions-service`).

### `notifications` — лог/очередь пользовательских уведомлений

Одна строка — одно уведомление одному конкретному получателю, `user_id` есть всегда. В отличие от `notification_triggers`, где строка описывает триггер целиком на группу получателей, без привязки к конкретному пользователю.

Таблица закрывает то, чего в Kafka нет:
- **идемпотентность** — `deduplication_key` с уникальным индексом не дает отправить одно и то же уведомление дважды, если сообщение из Kafka придет повторно (доставка at-least-once);
- **информативность** — можно посмотреть, что и когда было отправлено конкретному пользователю;
- **статус доставки** — `status`/`error_message` дают возможность различать "поставлено в очередь", "отправлено", "не удалось" и повторить неудачные попытки — в самой Kafka у сообщения нет изменяемого состояния.

| Поле | Тип | Назначение |
|---|---|---|
| `notification_id` | UUID, PK | идентификатор конкретного уведомления |
| `user_id` | UUID | получатель |
| `notification_type` | varchar, nullable | `user_registered`, `review_liked` и т.п. |
| `template_id` | UUID | шаблон, использованный для рендера |
| `channel` | enum: email / sms / push | канал доставки |
| `payload` | jsonb | данные для подстановки в шаблон |
| `delivery_address` | varchar, nullable | реальный адрес доставки на момент отправки (email/телефон/push-токен) |
| `status` | enum: pending / sent / failed / delivered / skipped | статус доставки, обновляется воркером; `skipped` — пользователь отключил канал в `user_notification_settings` |
| `created_at` | timestamp | когда событие принято |
| `sent_at` | timestamp, nullable | когда реально отправлено |
| `error_message` | text, nullable | причина сбоя — для ретраев и дебага |
| `deduplication_key` | varchar, nullable, unique | дедупликация при повторной доставке события из Kafka (at-least-once) |

### `templates` — шаблоны сообщений

Таблица `templates`:

| Поле | Назначение |
|---|---|
| `template_id` | PK |
| `code` | стабильный идентификатор для кода/каталога событий, например `new_episode_email` |
| `name` | название для админки, например «Новая серия (email)» |
| `channel` | email / sms / push |
| `subject` | тема письма, тоже с плейсхолдерами (например, `{{ series_title }}`) |
| `body` | текст с плейсхолдерами (например, `{{ episode_title }}`) |
| `allowed_variables` | список разрешенных плейсхолдеров (jsonb) — общий для `subject` и `body`; позволяет провалидировать `payload` до отправки, а не ловить опечатку в имени переменной постфактум |
| `is_active` | можно отключить старую версию, не удаляя |
| `created_at` / `updated_at` | даты создания и изменения |

При отправке воркер берет `template_id`, подставляет значения из `payload` через Jinja2 (`{{ var }}`) — получает готовый текст. `StrictUndefined`: если в `payload` не хватает переменной, которую ждет шаблон, рендер бросает исключение, а не подставляет пустую строку.

### `admin_mailings` — ручные рассылки из админки

По смыслу похоже на `notification_triggers`: и то, и другое разворачивается в множество строк `notifications`. Отличия:

- **триггер другой** — `notification_triggers` срабатывает автоматически по изменению контента, `admin_mailings` запускается человеком по кнопке "отправить";
- **не повторяется** — у триггера уведомления есть `check_interval`/`last_checked_at`, потому что он живет постоянно и переспрашивается; рассылка одноразовая — сработав однажды (`status → sending → sent`).

Для отложенной отправки `admin_mailings` тоже проверяется тем же шедулером, что и `notification_triggers`, только логика проще. Проверяется наступил ли `scheduled_at`. Если рассылка создана без указания времени (отправить сразу), шедулер не нужен, API публикует Kafka-триггер немедленно при создании.

Отложенная отправка задается не абсолютным моментом, а `scheduled_local_datetime` — датой и временем в таймзоне получателя. Одна такая рассылка на входе превращается в несколько строк `admin_mailings` — по одной на каждую таймзону, встречающуюся у аудитории.

| Поле | Тип | Назначение |
|---|---|---|
| `admin_mailing_id` | UUID, PK | идентификатор рассылки |
| `template_id` | UUID (FK) | какой шаблон использовать |
| `audience_filter` | jsonb | описание аудитории; при отложенной (запланированной) рассылке — в отличие от немедленной — сервис разбивает аудиторию по таймзонам и сам дописывает в него ключ `timezone` для каждого бакета |
| `payload` | jsonb | данные для подстановки в шаблон, общие для всех получателей рассылки |
| `status` | enum: scheduled / sending / sent / failed | статус всей рассылки целиком; черновика нет — запись сразу создается с одним из рабочих статусов (`scheduled` или `sending`, в зависимости от того, немедленная рассылка или отложенная) |
| `scheduled_at` | timestamp, nullable | когда отправить (для бакета — уже посчитанный под конкретную таймзону момент в UTC), если не сразу |
| `sent_at` | timestamp, nullable | когда рассылка реально завершена (переход в `sent`) |
| `created_by` | UUID | админ, создавший рассылку |
| `created_at` / `updated_at` | timestamp | даты создания и изменения |

Хранится в БД сервиса нотификаций. `movies_admin` держит только локальную копию.

### `user_notification_settings` — настройки уведомлений пользователя

Одна строка на пользователя — его собственные предпочтения: разрешил ли он уведомления вообще и по каким каналам. Без этой таблицы у широковещательной рассылки нет способа учесть "я не хочу получать SMS" или отписку целиком — она есть даже у ручных рассылок из админки, не только у контентных триггеров.

Воркер обязан проверить эту таблицу перед отправкой каждому получателю: если канал выключен (или `notifications_enabled = false`), в `notifications.status` пишется `skipped`, реальная отправка не делается.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID, PK | идентификатор записи |
| `user_id` | UUID, unique | пользователь (ссылка на пользователя в auth-service) |
| `notifications_enabled` | bool, default true | общий рубильник — уведомления разрешены |
| `email_enabled` | bool, default true | разрешен email |
| `sms_enabled` | bool, default false | разрешен SMS |
| `push_enabled` | bool, default true | разрешен push |
| `updated_at` | timestamp | когда пользователь последний раз менял настройки |

## Три категории уведомлений

Два независимых измерения: immediate/scheduled (публикует Kafka-триггер сразу источник события или шедулер по расписанию) × personal/group (один получатель, известный сразу, или аудитория, которую нужно резолвить).

- **Персональные / Immediate personal** — получатель один, известен сразу источнику события. Резолвить аудиторию не нужно, шедулер не участвует, Kafka-триггер не публикуется — сразу полностью собранное сообщение в `notification-ready`. Пример: лайк на рецензию (`user_actions-service` знает автора рецензии), регистрация пользователя.

- **Периодические-групповые / Scheduled group** — получателей много; Kafka-триггер публикует шедулер по итогам периодической проверки. Пример: новая серия сериала (`notification_triggers`, проверка по `check_interval`/`last_checked_at`), отложенная ручная рассылка с заданным `scheduled_local_datetime` (шедулер проверяет `admin_mailings`).

- **Мгновенные-групповые / Immediate group** — получателей много, фан-аут, но Kafka-триггер публикует сразу API, без участия шедулера. Пример: ручная рассылка из админки без `scheduled_local_datetime` — "отправить всем premium сейчас".

Четвертый тип, **Scheduled personal** - шедулер по расписанию проверяет условие персонально для каждого пользователя, срабатывание всегда дает одного получателя. Сейчас не используется.

## Каталог событий

- **Регистрация пользователя** — источник auth-service, получатель один, без периодичности. Перед отправкой auth-service зовет short-links-service (`create_short_link()`), чтобы получить `confirmation_link` для `payload` — если short-links-service недоступен, письмо не отправляется вообще (ошибка ловится раньше `notify_user()`).
- **Смена пароля** — источник auth-service, получатель один, без периодичности.
- **Лайк/дизлайк на вашу рецензию** — источник user_actions-service, получатель один, без периодичности.
- **Новая серия сериала** — источник movies_admin (`EpisodeAdmin.save_model()` при переходе эпизода в `RELEASED`), получатели — все пользователи, у кого этот сериал в закладках, срабатывает по изменению.
- **Ручная рассылка от админа** — источник админка, получатели зависят от выбранного сегмента, отправка сразу или отложенно с учетом таймзон (`scheduled_local_datetime`).

Чем можно расширить список событий (сейчас не реализовано):
- **сброс пароля по ссылке** — нет самого флоу в auth-service (есть только смена с текущим паролем);
- **автособытие «новый фильм добавлен в каталог»**;
- **новая рецензия на фильм из закладок** — сам механизм резолва аудитории по закладкам в воркере работает;
- **«истекает подписка» и «забытая закладка»** — оба одной формы: периодическая проверка по множеству пользователей, т.е. Scheduled personal — четвертый тип событий.

## Сценарии работы

### 1. Персональное уведомление (Immediate personal)

Получатель известен сразу источнику события. Пример: лайк на рецензию. `user_actions-service` в момент лайка уже знает автора рецензии (`user_id`).

1. Сервис-источник (любая часть сайта) вызывает API нотификаций с полностью готовым payload: `{user_id, template_id, payload}`. `channel` в запросе не передается — API берет его из самого шаблона (`template.channel`), чтобы канал не мог разойтись с шаблоном, который его определяет.
2. API валидирует запрос (например, что `template_id` существует и `payload` не содержит переменных, не входящих в `allowed_variables` шаблона — обратной проверки, что все `allowed_variables` присутствуют в `payload`, нет: если шаблону не хватит переменной при рендере, это уже ошибка воркера, а не 4xx на API) и публикует как есть в `notification-ready` — данные уже полностью собраны.
3. Воркер читает сообщение, создает строку в `notifications` (`status=pending`).
4. Проверяет `user_notification_settings` получателя: если нужный канал отключен (или `notifications_enabled=false`) — `status=skipped`, дальше не идет.
5. Иначе рендерит шаблон (`template_id` + `payload` → готовый текст), реально отправляет через провайдера канала (`email` — SMTP, `push` — публикация в Redis), записывает `delivery_address` (адрес/телефон/`user_id` для push на момент отправки) и итоговый `status` (`sent`/`failed`, с `error_message` при ошибке).

### 2. Периодические-групповые уведомления (Scheduled group)

Получателей много, точный список заранее не известен — нужен фан-аут. Kafka-триггер публикует не источник события напрямую, а шедулер, по итогам периодической проверки. Два независимых источника попадают в один и тот же механизм с шага 3.

**2a. Автоматический триггер уведомления.** Пример: вышла новая серия сериала X.

1. `movies_admin` при обновлении контента (например, релиз новой серии) вызывает API с `{content_id, notification_type, template_id, payload}`.
2. API делает upsert в `notification_triggers`: обновляет `template_id`/`payload`/`last_update = now()` для строки `(content_id, notification_type)` (создает строку, если ее еще не было).

**2b. Отложенная ручная рассылка.** Пример: админ создает рассылку и указывает время отправки на завтрашнее утро по местному времени получателей.

1. Админ в Django admin выбирает шаблон, сегмент аудитории (фильтр, не явный список `user_id`), меняет значение поля **Send** с дефолтного «отправить сразу» на «запланировать по местному времени получателя» и вводит дату/время (`ГГГГ-ММ-ДД ЧЧ:ММ`, местное время получателя, не UTC и не время браузера админа). Django вызывает API нотификаций с `{template_id, audience_filter, payload, scheduled_local_datetime, created_by}` — `admin_mailing_id` в запросе нет, он генерируется сервером на каждый бакет.
2. API резолвит уникальные таймзоны аудитории (`search_distinct_timezones` в auth-service) и создает по одной записи в `admin_mailings` со `status=scheduled` на каждую с уже посчитанным под конкретную таймзону `scheduled_at` в UTC.

**Дальше общий путь для 2a и 2b:**

3. Шедулер с заданной периодичностью проверяет оба источника: триггеры уведомлений в `notification_triggers`, где `now() >= last_checked_at + check_interval` (сравнивает `last_update` с `last_notification_sent` — реально ли что-то изменилось), и рассылки в `admin_mailings` со `status=scheduled`, где наступил `scheduled_at`.
4. Если триггер уведомления сработал (или для рассылки наступило время) — шедулер публикует неполный Kafka-триггер в `notification-pending` (одно сообщение на весь `content_id`/`admin_mailing_id`, не по одному на пользователя). Для рассылки дополнительно переводит `admin_mailings.status = sending`.
5. Воркер читает Kafka-триггер, резолвит аудиторию — для триггера уведомления, например, кто добавил сериал в закладки; для рассылки — запрос по `audience_filter` к auth-service/БД пользователей.
6. Для каждого пользователя из аудитории воркер сам собирает `ReadyMessage` — такой же по форме, как приходит извне в сценарии 1, но здесь его никто не присылал: `user_id` берется из результата резолва аудитории, остальные поля из исходного триггера/рассылки и шаблона (детерминированный `deduplication_key`, свой для триггера/рассылки — чтобы повторная публикация после NACK не задвоила уже обработанные сообщения получателю), и публикует его в **`notification-ready-bulk`** — фан-аут, а не обработка на месте. Реальная отправка (шаги 3–5 сценария 1: создать строку в `notifications`, проверить `user_notification_settings`, рендер, отправка) происходит уже в обработчике `notification-ready-bulk`, общем с `notification-ready`.
7. По завершении публикации всех сообщений (доставки асинхронная и произойдет позже, отдельными сообщениями) воркер обновляет источник: для триггера уведомления — `notification_triggers.last_notification_sent = now` (чтобы не сработать повторно на то же изменение); для рассылки — `admin_mailings.status = sent`.

### 3. Мгновенные-групповые уведомления (Immediate group)

Получателей тоже много, фан-аут нужен, но Kafka-триггер публикует сразу API — шедулер не участвует.

Пример: админ создает рассылку без указания времени — «отправить всем premium-пользователям прямо сейчас».

1. Админ в Django admin выбирает шаблон и сегмент аудитории, **Send** оставляет как «Send immediately» (по умолчанию). Django вызывает API с `{template_id, audience_filter, payload, created_by}` (`scheduled_local_datetime` не передается/`null`) — `admin_mailing_id` в запросе нет.
2. API сначала генерирует `admin_mailing_id` и публикует неполный Kafka-триггер в `notification-pending` — без похода через шедулер, и только потом создает запись в `admin_mailings` со `status=sending`. Порядок специально такой: если Kafka недоступна, публикация падает раньше записи в БД — не остается строки, зависшей в `sending` без единого отправленного сообщения; если наоборот упадет запись в БД уже после успешной публикации — письма все равно уйдут (воркеру для резолва и отправки достаточно данных из самого Kafka-сообщения), потеряется только запись о рассылке.
3. Дальше — шаги 5–7 из сценария 2: воркер резолвит сегмент, для каждого пользователя публикует `ReadyMessage` в `notification-ready-bulk` (фан-аут), по завершении публикации (не доставки) обновляет `admin_mailings.status = sent`. Сбой у отдельного получателя не прерывает обработку остальных — рассылка все равно доходит до `sent` (сбой уходит в DLQ).

Формат Kafka-триггера и обработка воркером идентичны сценарию 2 — разница только в том, кто и когда его публикует (API сразу vs шедулер по расписанию), поэтому весь путь после публикации триггера — общий код, а не дублирующая реализация.

## Push-уведомления (WebSocket)

Третий канал доставки, наряду с `email`/`sms`, без гарантии доставки:

1. Воркер (тот же шаг 5 сценария 1 / фан-аут в сценариях 2-3) публикует готовое сообщение в Redis Pub/Sub, канал `push:{user_id}`. `status=sent` означает, что опубликовано в Redis, а не доставлено клиенту.
2. `ws-gateway` подписан на все каналы `push:*`. Может работать в нескольких инстансах — Redis рассылает сообщение всем сразу, каждый инстанс проверяет свой локальный (in-memory) реестр открытых WebSocket-соединений и доставляет только тем, кто подключен именно к нему.
3. Если пользователь не подключен ни к одному инстансу, то сообщение теряется. Ретраев, DLQ и истории для push нет в отличие от email.

Клиент подключается на `ws://host/api/v1/ws/notifications?token=<JWT>` (тот же JWT, что и для остальных API, публичный ключ кэшируется в Redis). Формат входящих push-сообщений: `{"type": "notification", "user_id": "...", "subject": "...", "body": "..."}`; keepalive — `{"type": "ping"}`/`{"type": "pong"}`.

Сейчас push-шаблоны (`channel=push`) заводятся только через `movies_admin` — выбор канала есть в форме создания шаблона (`movies_admin/notifications/forms.py`). Остальные источники событий (`auth`, `user_actions`, `movies`) пока не заведены на push. Расширение на другие источники — задел на будущее.

**Экранирование.** Значения payload подставляются в `subject`/`body` как есть, без экранирования — `render()` использует Jinja `SandboxedEnvironment` с `autoescape=False`. Для push это уходит клиенту в JSON, и если фронтенд отрендерит `body` как HTML, пользовательский контент из payload (имя, заголовок фильма) может стать XSS у получателя. `SandboxedEnvironment` защищает только от выполнения кода на сервере, не от HTML-инъекции в текст.

Варианта два: включить autoescape или гарантировать экранирование на клиенте. Ни то, ни другое полностью не подходит: глобальный `autoescape=True` испортил бы email, который сейчас отправляется как `text/plain`, а гарантировать поведение клиента нельзя, так как фронтенда для push пока не существует. Поэтому `render()` (`worker/render.py`, `src/render.py`) принимает `escape_html: bool`: для `channel=push` значения payload экранируются через `html.escape()` перед подстановкой, для остальных каналов нет. Экранирование сознательно сделано на сервере, а не оставлено на будущий клиент.

Превью шаблона в `movies_admin` (`preview_template.html`) рендерит `subject`/`body` без фильтра `|safe` — с ним Django-автоэкранирование отключалось, и payload/шаблон, введенные в форму превью, выполнялись как HTML в браузере админа.
