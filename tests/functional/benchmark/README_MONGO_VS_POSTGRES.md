Для реализации хранения, накопления информации от пользователей(лайки, закладки)
решили реализовать отдельный сервис: аналитика будет расти, для разделения отвественности
решили не смешивать разные сушности (события и взаимодействие с контентом)

При выборе хранилища для нового сервиса остановились на MongoDB и Postgresql. 
Для выбора, провели замер производительности для MongoDB и Postgresql.
Проверяли: наполнение таблиц (данные рассчитаны для 10 000 фильмов и 10 000 пользователей,
оценили, что 50% фильмов/сериалов получит лайк, 10% фильмам будет добавлена рецензия,
10% будут добавлены в закладки)

Проведены следующие тесты:
1) Измерить скорость добавления данных
2) Тестирование чтения уже загруженных данных. 
- список понравившихся пользователю фильмов (список лайков пользователя);
- количество лайков или дизлайков у определённого фильма;
- список закладок;
- средняя пользовательская оценка фильма.
3) Тестирование чтения данных, поступающих в реальном времени:
- добавление лайка или дизлайка и время появления лайка или дизлайка

## 🎯 ИТОГОВЫЙ ВЫВОД ПО ВЫБОРУ ХРАНИЛИЩА

### Рекомендуемое решение: **PostgreSQL**

По результатам комплексного тестирования для хранения пользовательских данных (лайки, закладки, рецензии) 
выбрана СУБД **PostgreSQL**.

### ✅ Обоснование выбора PostgreSQL

#### 1. **Производительность чтения**
PostgreSQL показала **в 2 раза более высокую скорость чтения** по всем тестовым запросам:
- Средняя оценка фильма: 0.7 мс (PostgreSQL) vs 1.4 мс (MongoDB)
- Количество лайков/дизлайков: 0.5 мс vs 1.5 мс
- Список лайков пользователя: 0.5 мс vs 0.7 мс
- Список закладок: 0.5 мс vs 0.7 мс

#### 2. **Стабильность под нагрузкой**
При конкурентной записи PostgreSQL демонстрирует **меньшую деградацию** производительности:
- Среднее замедление запросов: 144% (PostgreSQL) vs 174% (MongoDB)
- Максимальное время отклика под нагрузкой: 6.7 мс vs 22.3 мс

#### 3. **Realtime-доступность данных**
Время появления новых данных в результатах запросов:
- PostgreSQL: **0.3–0.4 мс**
- MongoDB: **1.2–2.1 мс**

#### 4. Postgres предоставляет разные уровни изоляции
Postgresql предоставляет разные варианты чтения(через уровни транзакиций), что дает возможность более чистого
чтения пользовательских данных.

#### 5. **Операционные преимущества**
- ✅ **Единая СУБД на проекте** — упрощает администрирование и мониторинг
- ✅ **Межкомандное взаимодействие** — общая экспертиза и инструменты
- ✅ **Меньше затрат на инфраструктуру** — не требуется отдельный кластер MongoDB

**Вывод:** Несмотря на более высокую скорость записи в MongoDB, для сценария UGC-сервиса выбор PostgreSQL 
является более оптимальным решением.
